# 用途別ガイド

## このガイドの目的

対象システムや作りたい資料によって、重視する点は変わります。このガイドでは、よくある用途ごとに、使う設定と確認方法を説明します。

詳しい設定値は[06_CUSTOMIZATION_EXAMPLES.json](06_CUSTOMIZATION_EXAMPLES.json)にあります。使いたい設定例を一つ選び、`CUSTOMIZATION_OVERRIDE`としてプロンプトと一緒に渡します。

## まず用途を選ぶ

| 用途 | 選ぶ設定 | 特に確認すること |
|---|---|---|
| 情報が少ない企画初期 | 既定設定 | 関係者の見落とし、AI推測の区別 |
| 短時間で小さな初稿を作る | `fast_small_bundle` | 出力の長さ、レビュー時間 |
| 製造設備を考える | `manufacturing_equipment_concept` | 安全、保守、異常停止、接続 |
| ソフトウェア中心のシステムを考える | `software_intensive_system` | API、データ、運用、セキュリティ |
| 安全に関係するシステムを考える | `safety_related_concept` | 根拠のない数値、ハザード、人の確認 |
| 初稿をさらに詳しくする | `detailed_60_point_followup` | 上位情報との一致、変更の影響 |
| 組織で繰り返し使う | 個別設定 | 再現性、記録、機械的な検査 |

## 共通の実行手順

どの用途でも、基本的な流れは同じです。

1. 対象システムの目的と、分かっている情報を書きます。
2. [01_CORE_PROMPT.md](01_CORE_PROMPT.md)とREADMEに記載した設定・規則ファイルを渡します。
3. 必要なら、用途に合う`CUSTOMIZATION_OVERRIDE`を追加します。
4. 生成されたZIPを開きます。
5. まず概要、主な仮定、主なリスク、人が確認する項目を読みます。
6. 確認した内容を次の入力へ追加し、必要なら再実行します。

## 1. 情報が少ない企画初期

### こんなときに使う

- アイデアはあるが、要求や構成がまだ決まっていない。
- 誰に話を聞くべきか分からない。
- 白紙から資料を作るのが難しい。

### この設定で行うこと

AIは、利用者だけでなく、運用、保守、製造、安全、試験などの関係者も候補にします。足りない情報は仮定として補います。

### 手順

1. 既定設定で実行します。
2. `14_human_confirmation_backlog.md`を開きます。
3. `critical`と`high`に分類された項目から確認します。
4. AIの仮定が正しいか、関係者に確認します。

### 結果を見るポイント

- 関係者ごとに、必要かどうかと理由が書かれているか。
- AIの推測が、人の確認済み情報として扱われていないか。
- TBDだけではなく、レビューできる候補が書かれているか。
- ニーズから要求までつながっているか。

## 2. 短時間で小さな初稿を作る

### こんなときに使う

- まず全体像だけを短時間で見たい。
- 長い出力を読む時間がない。
- AIの出力が途中で切れることを避けたい。

### この設定で行うこと

成果物の種類は残したまま、関係者、要求、構造、接続の件数を減らします。詳しい説明よりも、重要な内容を優先します。

### 手順

1. `fast_small_bundle`を選びます。
2. 概要、主な仮定、主なリスクを先に読みます。
3. 詳しくしたい部分を決めます。
4. 次の実行で、その部分に関する上限だけを増やします。

### 結果を見るポイント

- 必要なファイルがすべて作られたか。
- 重要なニーズやリスクが省かれていないか。
- 通常設定より短い時間でレビューできたか。

## 3. 製造設備を考える

### こんなときに使う

- 搬送設備、検査設備、組立設備などを考える。
- 機械、電気、制御、ソフトウェア、人の作業が関係する。
- 異常停止や保守も早い段階から考えたい。

### この設定で行うこと

機械とソフトウェアだけでなく、作業者、保守手順、設備、材料も候補にします。通常運転だけでなく、異常、停止、復旧、保守の場面も作ります。

### 手順

1. `manufacturing_equipment_concept`を選びます。
2. 対象物、既存設備、作業者の役割、運転モードを入力します。
3. 電源、信号、材料、機械接続、人とのやり取りを確認します。
4. 安全に関係する数値は、根拠が確認できるまで候補のままにします。

### 結果を見るポイント

- 運用者、保守者、設置者、安全担当が検討されているか。
- 異常を見つける人や機能、停止させる人や機能が明確か。
- 必要な機能と、実際の装置が分けて書かれているか。
- 接続の両端、流れるもの、方向、単位、時間が書かれているか。

## 4. ソフトウェア中心のシステムを考える

### こんなときに使う

- Webサービス、業務システム、データ処理システムを考える。
- 外部APIや外部サービスが多い。
- データ品質、監査、障害復旧が重要である。

### この設定で行うこと

画面や内部処理の一覧だけでなく、利用者が達成したい目的を中心に整理します。API、データ、運用責任、障害時の動作も候補にします。

### 手順

1. `software_intensive_system`を選びます。
2. 主な利用者、外部API、データの提供者と利用者を入力します。
3. 障害が起きたときに期待する動作を入力します。
4. APIの形式、データの型、送る頻度、失敗時の動作を確認します。

### 結果を見るポイント

- 利用者が何を達成したいかが分かるか。
- 外部APIと関連する要求、試験がつながっているか。
- 可用性、性能、セキュリティ、個人情報、保守が検討されているか。
- 根拠のないクラス名やソースコードを、決定済みとして扱っていないか。

## 5. 安全に関係するシステムを考える

### こんなときに使う

- 故障や誤動作が、人や環境へ大きな被害を与える可能性がある。
- 安全性能や適用規格を、専門家が確認する必要がある。

### この設定で行うこと

安全に関係する数値、規格、リスクの受け入れは、AIだけで決定しません。人の確認が必要な項目として目立たせます。

ハザードとは、人や物へ害を与える可能性がある状態や条件です。故障モードとは、部品や機能が期待どおりに動かない状態です。この二つを分けて整理します。

### 手順

1. `safety_related_concept`を選びます。
2. 安全分類、適用規格、性能値を未確認情報として扱います。
3. 各ハザードについて、原因、影響、予防、被害を小さくする方法、復旧を確認します。
4. 安全担当者、法務・規制担当者、試験責任者に確認項目を割り当てます。

### 結果を見るポイント

- 根拠のない数値が確定情報になっていないか。
- ハザードから対策と試験までつながっているか。
- 適用規格とリスク受け入れが未確認だと分かるか。
- 出力が安全認証の証拠ではないと明記されているか。

## 6. 初稿をさらに詳しくする

### こんなときに使う

- 最初の初稿を人がレビューした。
- 確認済み情報を使って、構成要素や試験を詳しくしたい。

### この設定で行うこと

最初のAI仮定をそのまま使わず、確認した情報を基に詳細化します。上位の情報を変えた場合は、影響を受ける下位の要求や設計も見直します。

### 手順

1. 人が確認する項目をレビューします。
2. 各項目を、確認済み、却下、保留に分けます。
3. 結果を入力へ戻します。
4. `detailed_60_point_followup`を選んで再実行します。

### 結果を見るポイント

- 確認していない仮定を基に、詳しい設計を作っていないか。
- 上位情報を変えたとき、古くなった下位情報が分かるか。
- JSON、Markdown、CSV、SysML仕様の名前と数値が一致するか。
- 詳細化した理由を上位の要求やリスクから説明できるか。

## 7. 組織で繰り返し使う

### こんなときに使う

- 複数の人が同じ方法で初稿を作りたい。
- 実行結果を比較したい。
- JSONの検査やZIP作成を確実に行いたい。

### この設定で行うこと

プロンプト、設定、検査ルール、Schemaを別ファイルで管理します。文章作成はAIに任せ、JSON検査、ID検査、ハッシュ計算などはプログラムへ任せることもできます。

### 手順

1. 少数のテーマで、カスタムGPTを使って試します。
2. ファイル不足、JSONエラー、参照エラーの件数を記録します。
3. 間違いを減らしたい検査だけを、外部プログラムにします。
4. 専用画面や外部システム連携が必要になったら、ChatGPT Appを検討します。

詳しくは、[13_CHATGPT_DISTRIBUTION_GUIDE.md](13_CHATGPT_DISTRIBUTION_GUIDE.md)と[14_CHATGPT_APP_CONCEPT_SPEC.md](14_CHATGPT_APP_CONCEPT_SPEC.md)を参照してください。

### 結果を見るポイント

- 同じ入力と設定で、結果を比較できるか。
- 使用したプロンプト、設定、AIモデル、日時を記録できるか。
- JSONエラーや存在しないIDを機械的に見つけられるか。
- 秘密情報を公開ファイルや不要なログへ入れていないか。
