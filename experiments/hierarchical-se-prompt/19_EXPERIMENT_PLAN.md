# 0点→40点の実験計画

## この実験で確かめること

このプロンプトが「正しい設計を自動で完成させる」かではなく、情報が少ない状態から人がレビューを始められる初稿候補を作れるかを調べます。

| Research Question | 確かめたいこと |
|---|---|
| RQ-A | `reviewable_40_candidate`へ到達する割合 |
| RQ-B | 現行プロンプトが簡易SEプロンプトよりよいか |
| RQ-C | Stop Ruleで過剰設計が減るか |
| RQ-D | Self Reviewと独立Reviewerがどの程度一致するか |
| RQ-E | Reviewerのモデルを変えると判定がどう変わるか |
| RQ-F | 人の作業が、作成から確認・選択へ移るか |
| RQ-G | 日本語の文章品質と要求の意味的妥当性を分けて評価できるか |

## 比較する条件

| 条件 | 内容 |
|---|---|
| B0 | 一般的な簡易SEプロンプト。ベースラインとして使う |
| B1 | 現在の`hierarchical-se-prompt` |
| B2 | B1の生成物を、40点Gateと独立AI評価プロトコルで評価する条件 |

B2は、生成用コアプロンプトを変更する条件ではありません。評価方法を追加した場合の違いを測る条件です。入力、モデル、温度など、比較に影響する設定を記録します。

## Pilotの規模

最初から大規模にせず、次の54実行を目安にします。

`3ドメイン × 2入力レベル × 3条件（B0/B1/B2） × 3回 = 54実行`

ドメインは、製造設備、ソフトウェア中心、安全関連などから選びます。入力レベルは「情報が少ない」と「ある程度情報がある」の2種類にします。3回という回数は最終的な統計保証ではなく、実行ごとのばらつきを知るための初期値です。

## 1実行で記録する項目

- 実験ID
- ドメインと入力レベル
- 条件（B0/B1/B2）
- 入力のハッシュまたは匿名化した識別子
- 使用モデルの正確な識別子
- 実行日時と設定
- プロンプト、設定、Schemaの版
- 出力ZIPと中心JSONのハッシュ
- ReviewerのTier（J0～J4）
- Gate状態
- 主要Traceの件数と割合
- Hard Blockerの件数
- `linguistic_quality`と`semantic_validity`の判定
- 人が採用、修正、却下した候補の数
- 初稿作成とレビューにかかった時間

入力に秘密情報や個人情報を含めないでください。実験結果を公開するときは、入力と出力を匿名化します。

## 比較する指標

主な指標は、次のように定義します。

- **Gate通過率**：`reviewable_40_candidate`の実行数 ÷ 全実行数
- **過剰設計率**：`overspecified_beyond_40`の実行数 ÷ 全実行数
- **Trace coverage**：対象関係を持つ主要項目のうち、追跡可能な項目の割合
- **Human question数**：確認・選択・承認が必要な質問の数
- **False Pass**：AIがGateを通した後、人の校正でHard Blockerが見つかった割合
- **Reviewer不一致率**：独立ReviewerのGate状態が一致しなかった割合
- **レビュー時間**：成果物を読んで確認項目を整理する時間

数値は比較のための指標です。数値がよくても、安全、法規、契約、承認の判断をAIへ移してはいけません。

## Pilot後の判断

Pilot後に、次を確認します。

1. B1とB2でGate通過率、過剰設計率、レビュー時間がどう変わったか。
2. Reviewerが見逃したHard Blockerがないか。
3. 40点の初期閾値が厳しすぎる、または緩すぎる箇所がないか。
4. 人の質問が本当に確認・選択中心になっているか。
5. 次の実験でモデル数、実行回数、ドメインを増やす必要があるか。

変更した閾値や判定方法は、実験版と理由を記録します。結果が良かった例だけでなく、Gateに失敗した例も残します。
