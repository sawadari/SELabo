# 階層型SE初稿生成プロンプト

## まず知ってほしいこと

このプロンプトは、対象システムについて分かっていることが少ない段階で、話し合いの土台となる初稿をAIに作らせるものです。

ここでいう「40点程度の初稿」とは、不完全でもレビューを始められる資料という意味です。品質を採点して40点と評価するわけではありません。生成後は、[40点GateとStop Rule](17_FORTY_POINT_GATE.md)で`below_reviewable`、`reviewable_40_candidate`、`overspecified_beyond_40`のいずれかに分類します。

AIが作った内容は、すべて候補です。正式な要求、承認済みの設計、規格への適合結果にはなりません。

## この実験で作りたい流れ

プロンプトは、次の順で情報をつなげます。

1. 誰が関係するか
2. その人や組織は何を望むか
3. システムは何をする必要があるか
4. どのように動くか
5. どのような部品、人、ソフトウェア、手順で実現するか
6. 部分同士をどう接続するか
7. 要求を満たしたことをどう確かめるか

このつながりを残すことで、「この要求はなぜ必要か」「この試験は何を確かめるのか」を後から確認しやすくします。

## よく出てくる言葉

| 言葉 | この実験での意味 |
|---|---|
| 対象システム | 今回考える製品、サービス、設備、業務など |
| 利害関係者 | 利用者、運用者、保守担当、顧客など、対象システムに関係する人や組織 |
| ニーズ | 利害関係者が実現したいこと |
| 要求 | システムや構成要素が満たすべきこと |
| トレーサビリティ | ニーズ、要求、設計、試験のつながりを追えること |
| 正本 | 同じ情報が複数あるときに、基準として扱う一つのデータ |
| SysML | システムの要求、構造、動作などを図やモデルで表すための言語 |
| Schema | JSONの項目やデータ形式が正しいかを確認するルール |

## 使い方

[01_CORE_PROMPT.md](01_CORE_PROMPT.md)と、次のファイルをChatGPTへ一緒に渡します。

- [02_DEFAULT_PROFILE.json](02_DEFAULT_PROFILE.json)：標準の設定
- [03_OUTPUT_CONTRACT.json](03_OUTPUT_CONTRACT.json)：作るファイルの一覧とルール
- [04_QUALITY_RULES.md](04_QUALITY_RULES.md)：結果を確認するルール
- [10_JAPANESE_TECHNICAL_WRITING_STANDARD.md](10_JAPANESE_TECHNICAL_WRITING_STANDARD.md)：日本語の書き方
- [11_JAPANESE_WRITING_PROFILE.json](11_JAPANESE_WRITING_PROFILE.json)：日本語ルールの機械可読版
- [schemas/se_model.schema.json](schemas/se_model.schema.json)：中心となるJSONの形式

### 実行手順

1. ChatGPTで、対象システムの目的と分かっている情報を説明します。
2. 上のファイルを渡します。
3. `01_CORE_PROMPT.md`の処理を実行するよう依頼します。
4. 出力されたZIPと「人が確認する項目」をレビューします。
5. 確認した内容を次の入力へ追加し、必要ならもう一度実行します。40点Gateを通過した後の詳細化は、別の実験として人が開始します。

用途に合う設定は、[05_USE_CASE_GUIDE.md](05_USE_CASE_GUIDE.md)から選べます。設定例は[06_CUSTOMIZATION_EXAMPLES.json](06_CUSTOMIZATION_EXAMPLES.json)にあります。

## 出力件数の扱い

この版では、関係者、ニーズ、要求、構造、インターフェース、説明の件数に、SELabo独自の人工的な上限を設けません。情報を減らすのではなく、すべての候補と不確実性を残します。

ただし、モデルのコンテキスト長、APIの応答上限、ファイル生成機能、実行時間には上限があります。実行環境で途中終了した場合は、成功したと報告せず、対象範囲を分割して再実行し、IDとトレーサビリティを統合します。

## AIが情報を補う理由

企画の初期には、保守担当者や試験担当者などの情報が抜けていることがあります。そこでAIは、一般的なSEの視点から不足しそうな項目を候補として追加します。

ただし、AIの推測を事実として扱わないように、各項目へ次の情報を付けます。

- どこから得た情報か
- 事実、推測、仮定のどれか
- 決定済みか、提案中か
- 現在も有効か
- 正式な基準に含まれるか
- AIがどの程度確信しているか

## L0～L7とは

L0～L7は、考える順番を示すためのこの実験独自の区分です。国際規格やSysMLが決めた唯一の階層ではありません。

| 段階 | 主に考えること |
|---|---|
| L0 | 目的、価値、対象範囲、周囲の環境 |
| L1 | 利害関係者、ニーズ、利用場面 |
| L2 | システム全体の要求と外から見た動き |
| L3 | 必要な機能と役割分担 |
| L4 | 機械、ソフトウェア、人、手順などの実現方法 |
| L5 | 機械、電気、ソフトウェアなど専門分野ごとの設計 |
| L6 | 構成要素の詳しい設計候補 |
| L7 | 実装、製造、設定、単体試験の候補 |

情報が足りないとき、L6とL7は具体的な部品やコードを決めず、実装方法の候補だけを示します。

## 一つの正本から複数の資料を作る

中心となるデータは`10_se_model.json`です。Markdown、CSV、SysMLモデル仕様は、このJSONから作ります。

同じ内容を別々に書くと、名前や数値がずれることがあります。一つの正本から作ることで、このずれを減らします。

## SysMLについて

既定ではSysML 1.7を対象にします。ただし、生成するのは特定ツールに直接読み込めるモデルではなく、モデルを作るための仕様候補です。

使用するツール、バージョン、交換形式が決まっていない場合、XMI（モデリングツール間でデータを交換する形式）などの互換性を保証しません。

## 結果をどう評価するか

生成後の標準評価は、[独立AI評価プロトコル](18_AI_EVALUATION_PROTOCOL.md)に従います。まず40点Gateを判定し、その後に同じ入力で複数回実行して次を比べます。

- 関係者の見落としが減ったか
- ニーズから要求、要求から試験までつながっているか
- 曖昧な要求文が何件あったか
- 存在しないIDを参照していないか
- 人が採用、修正、却下した候補はどのくらいか
- 初稿作成とレビューに何分かかったか
- `linguistic_quality`と`semantic_validity`を分けた判定
- AI評価が見逃した重大Finding（False Pass）

## 調査結果を反映した改善の範囲

今回の版では、以前の指定どおり`01_CORE_PROMPT.md`の本文を変更していません。40点の判定、独立評価、実験計画、情報源の境界を、生成後に使う文書として追加し、設定・出力契約から人工的な件数上限と圧縮方針を撤廃しています。これにより、生成体験を変えずに「本当にレビュー可能か」を測定できます。

## できないこと

この実験だけでは、要求や設計が正しいとは証明できません。規格適合、認証、法令、安全性、サイバーセキュリティ、正確な性能値、部品選定には、専門家の確認が必要です。

実施済みの検査と未実施の検査は、[07_VALIDATION_REPORT.md](07_VALIDATION_REPORT.md)にまとめています。
