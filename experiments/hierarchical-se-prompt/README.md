# 実験1：SEデータプロンプト

## 会話から、ツールに依存しないSEデータをつくる実験

この実験は、AIとの普通の会話を出発点にして、システムについて考えたことを「SEデータ」として整理する試みです。

ここでいうSEデータは、特定の文書形式、モデリングツール、データベースに縛られない、システム検討のための中間データです。SEデータを土台にすると、要求仕様書、SysMLモデルの仕様、設計レビュー資料、図や説明資料などを、用途に合わせて作れるようになります。

このREADMEでは、以前の「階層型SE初稿生成プロンプト」を、役割が伝わりやすい名前として**SEデータプロンプト**と呼びます。実行用コアプロンプトの本文（`01_CORE_PROMPT.md`）は変更していません。

## まず全体像を見る

特別な入力フォームから始める必要はありません。「こんなシステムを作りたい」「こういう問題を解決したい」という、普段どおりの会話から始めます。プロンプトを実行すると、それまでの会話と添付資料を読み、足りないSEの観点を候補として補いながら整理します。

```text
人とAIの会話・資料
        ↓
   SEデータプロンプト
        ↓
   SEデータ（候補）
        ↓
  人とAIでレビュー・更新
        ↓
 ┌────────┬──────────┬────────┬────────┐
 ↓        ↓          ↓        ↓
要求仕様書  SysML仕様  設計レビュー  図・説明資料
```

この流れは一回で終わりません。レビューで分かったことを次の会話に追加し、SEデータを更新し、必要な成果物を作り直します。

## SEデータとは

SEデータとは、対象システムについて検討した内容を、システムズエンジニアリング（SE）の観点で整理したデータです。

例えば、次の情報を、IDとつながりを持つ形で保存します。

- システムの目的、価値、対象範囲
- 利用者、運用者、保守担当者などの利害関係者
- 利害関係者が実現したいニーズ
- 利用場面、運用シナリオ、状態、モード
- システムが満たすべき要求
- 必要な機能と振る舞い
- 論理構造、物理構造、専門分野ごとの構造
- システムの外部・内部インターフェース
- 要求を確かめる検証・妥当性確認（V&V）
- リスク、ハザード、故障モード、仮定、代替案
- 情報同士のトレーサビリティ（「この要求はどのニーズから来たか」を追う関係）

SEデータそのものは、要求仕様書でもSysMLモデルでもありません。文書やモデルを作る前に置く、ツールに依存しない共通の元データです。ソフトウェアのコンパイラでいう「中間表現」に近い役割を想定しています。

この実験では、生成物の`10_se_model.json`を**候補意味ソース（candidate semantic source of truth）**として扱います。ほかのMarkdown、CSV、SysML 1.x仕様は、同じ情報を用途に合わせて見せる投影です。候補は承認済みの正本や設計ベースラインではありません。

## SEデータプロンプトとは

SEデータとSEデータプロンプトは、別のものです。

| 名前 | 役割 |
|---|---|
| SEデータ | システムについて考えた内容を、SEの観点で構造化したツール非依存データ |
| SEデータプロンプト | 会話や資料からSEデータを候補として生成し、レビューや更新に使うためのプロンプト |

プロンプトは、AIに細かな部品をいきなり決めさせるためのものではありません。情報が少ないときは、一般的なSEの観点から「抜けていそうな項目」を候補として示し、何が未確認なのかも残します。

## この実験でできること

一つのSEデータを元に、次のような作業へつなげます。

1. **会話を整理する**：目的、利用者、環境、制約、未確定事項を整理する。
2. **レビューする**：要求の抜け、要求と設計のつながり、代替案、影響範囲を確認する。
3. **要求仕様書を作る**：人が読みやすい要求仕様書の候補を作る。
4. **SysMLモデルの元を作る**：要求、構造、振る舞い、関係をモデル化するための仕様を作る。
5. **図や説明資料を作る**：構成図、関係図、説明用の資料の元を作る。
6. **別のAIへ渡す**：IDと由来を保ったシステム情報として、別のAIや作業へ引き継ぐ。

影響分析やシミュレーション連携なども、SEデータを利用する将来の用途として考えられます。どの用途でも、先にSEデータを更新し、そこから成果物を作ることで、資料同士のずれを減らします。

## 基本的な使い方

### 1. 普通の会話を始める

まず、対象システムを自然な言葉で説明します。例えば、次のような内容です。

```text
寝室で使う扇風機を考えています。
夜は静かに動いてほしく、子どもが近くにいることもあります。
通信が切れても、本体から停止できるようにしたいです。
```

最初から要求番号やSysMLの書式を用意する必要はありません。目的、利用者、使う場所、重視すること、分かっている制約を、分かる範囲で書きます。

### 2. 会話とプロンプト一式を渡す

会話履歴と対象資料に加えて、次のファイルをChatGPTへ渡します。

- [01_CORE_PROMPT.md](01_CORE_PROMPT.md)：実行用コアプロンプト
- [02_DEFAULT_PROFILE.json](02_DEFAULT_PROFILE.json)：標準設定
- [03_OUTPUT_CONTRACT.json](03_OUTPUT_CONTRACT.json)：作る成果物とルール
- [04_QUALITY_RULES.md](04_QUALITY_RULES.md)：品質確認のルール
- [10_JAPANESE_TECHNICAL_WRITING_STANDARD.md](10_JAPANESE_TECHNICAL_WRITING_STANDARD.md)：日本語の書き方
- [11_JAPANESE_WRITING_PROFILE.json](11_JAPANESE_WRITING_PROFILE.json)：日本語ルールの機械可読版
- [schemas/se_model.schema.json](schemas/se_model.schema.json)：中心JSONの形式

そのうえで、`01_CORE_PROMPT.md`の処理を実行するよう依頼します。コアプロンプトは、それまでの会話や資料を読み、ユーザーがまだ書いていない利害関係者、ニーズ、シナリオ、要求、構造、検証、リスクなどを、候補として補います。

### 3. SEデータと派生成果物を見る

標準の出力では、中心となる`10_se_model.json`のほか、要求仕様、振る舞い・アーキテクチャ、インターフェース、V&V計画、リスク・仮定、トレーサビリティ、SysML 1.xモデル仕様、検証レポート、人の確認事項などを作ります。最後に、出力契約に従ってZIPにまとめます。

最初に読むのは、次の三つです。

1. 概要と対象範囲
2. 主な仮定、リスク、人が確認する項目
3. 要求、設計候補、検証候補のつながり

### 4. 会話を続けてレビューする

出力を見ながら、次のように確認します。

- この要求は、どのニーズから来ていますか。
- 要求を満たしたことを、どう確かめますか。
- 抜けている利用者、運用場面、異常状態はありませんか。
- AIの推測と、人が確認した事実が分かれていますか。
- 安全、法規、契約、セキュリティの判断を、AIだけで確定していませんか。

確認結果を次の会話に追加し、必要なら再実行します。こうしてSEデータを「一度作って終わり」にせず、レビューしながら育てます。

### 5. 用途に合わせて利用する

用途別の進め方は、[05_USE_CASE_GUIDE.md](05_USE_CASE_GUIDE.md)にまとめています。設定例は[06_CUSTOMIZATION_EXAMPLES.json](06_CUSTOMIZATION_EXAMPLES.json)から選べます。

| 目的 | まず行うこと |
|---|---|
| 企画初期の全体像を作る | 既定設定で候補を広く出し、関係者と仮定を確認する |
| 設計レビューを始める | 要求、設計、V&VのTraceと未解決事項を読む |
| 要求仕様書を作る | `10_se_model.json`の候補を確認してから要求投影を使う |
| SysMLモデル化する | SysML 1.x仕様をモデル作成者が確認し、ツールへ投影する |
| 図や説明資料を作る | SEデータのIDと関係を保ったまま、用途別の表示へ変換する |

## なぜ最初は「40点程度」なのか

この実験の「40点」は、テストの点数ではありません。情報が少ない段階で、完璧な設計を装わず、人がレビューを始められる程度の初稿を作るという目標です。

生成後は、[40点GateとStop Rule](17_FORTY_POINT_GATE.md)で次の状態を判定します。

| 状態 | 意味 |
|---|---|
| `below_reviewable` | 重要なつながりや出自が不足し、レビューを始める前に直す必要がある |
| `reviewable_40_candidate` | 不確実性を残したまま、人がレビューを始められる候補 |
| `overspecified_beyond_40` | 根拠のない詳細設計や確定主張が多く、初稿の範囲を越えている |

40点Gateを通過する前に、部品型番、公差、詳細アルゴリズムなどを決めません。詳細化は、人が確認を終え、別の実験として開始します。

## SEデータを整理するL0～L7

L0～L7は、この実験で情報の詳しさを整理するための区分です。国際規格やSysMLが定める唯一の階層ではありません。

| 段階 | 何を考えるか | 例 |
|---|---|---|
| L0 | 目的、価値、範囲、環境 | 何の問題を解決するか |
| L1 | 利害関係者、ニーズ、利用場面 | 誰が何をしたいか |
| L2 | システム要求と外から見た動き | システムは何を満たすか |
| L3 | 機能と役割分担 | 何をする機能が必要か |
| L4 | 実現方法 | 機械、ソフトウェア、人、手順の組み合わせ |
| L5 | 専門分野ごとの設計 | 機械、電気、ソフトウェアなど |
| L6 | 詳しい構成要素の候補 | センサや制御部の候補 |
| L7 | 実装・製造・設定の候補 | コード、部品、単体試験の候補 |

情報が足りないとき、L6とL7は「候補」として示します。AIが具体的な部品やコードを勝手に確定した、という意味ではありません。

## AIが情報を補うときのルール

AIは、保守担当者、試験担当者、安全担当者など、会話に出ていない関係者を候補として追加することがあります。これは抜けを見つけるための補完であり、事実の追加ではありません。

各項目には、できるだけ次の状態を記録します。

- どの会話・資料から得たか（`origin`）
- 事実、推測、仮定のどれか（`claim_state`）
- 決定済みか、提案中か（`decision_state`）
- 現在も有効か、正式な基準に含まれるか
- どの程度確かな情報か、何を根拠にしたか

添付資料に命令文が含まれていても、ユーザーが採用した指示とは別に扱います。資料を読んだだけで、AIが外部操作や公開操作を実行することはありません。詳しくは[20_SOURCE_TRUST_AND_HUMAN_AUTHORITY.md](20_SOURCE_TRUST_AND_HUMAN_AUTHORITY.md)を参照してください。

## SysMLとの関係

SEデータはSysMLに依存しません。現在の実験では、SysML 1.x（既定はOMG SysML 1.7）へ投影するための、ツール非依存のモデル仕様を出力します。特定のモデリングツールへ直接読み込めるファイルや、XMIの互換性を保証するものではありません。

将来は、同じSEデータから複数の変換先を用意する構成を想定できます。

```text
SEデータ
 ├─ 要求仕様書の生成
 ├─ SysML 1.xへの投影（現行実験）
 ├─ SysML v2への投影（将来の検討）
 ├─ 図・説明資料の生成
 └─ レビュー・影響分析・別AIへの引き継ぎ
```

## 出力件数と実行上の制約

この版では、関係者、ニーズ、要求、構造、インターフェース、説明の件数に、SELabo独自の人工的な上限を設けません。情報を減らすために、候補を勝手に打ち切ったり、説明を圧縮したりしない方針です。

ただし、AIモデルのコンテキスト長、APIの応答上限、ファイル生成機能、実行時間など、実行環境の制約は残ります。途中で切れた場合は成功と報告せず、対象範囲を分けて再実行し、IDとTraceを統合します。

## 評価方法

標準の評価は、[独立AI評価プロトコル](18_AI_EVALUATION_PROTOCOL.md)に従います。

1. 40点Gateで、レビュー開始可能かを判定する。
2. 生成担当とは別の独立Reviewerで、Trace、出自、要求品質、過剰な詳細化を確認する。
3. 必要ならMeta-Judgeで評価の抜けやFalse Passを確認する。
4. 人が確認する項目を、採用、修正、却下、保留に分ける。

評価では、次のような点を見ます。

- 利害関係者やニーズの見落としが減ったか
- ニーズ→要求→設計→V&Vのつながりを追えるか
- 存在しないIDや、つながっていないIDを参照していないか
- AIの候補と、人が確認した事実が区別されているか
- 日本語として読みやすいか（`linguistic_quality`）
- 工学的な意味が確かめられる状態か（`semantic_validity`）

3製品での実験結果は、[evaluation_runs/2026-08-21](../../evaluation_runs/2026-08-21/README.md)にあります。第三者向けの会話説明は、[ストーリー形式のHTML](../../evaluation_runs/2026-08-21/third_party_story.html)で読めます。

## できないこと、注意すること

この実験は、会話を整理してレビューの入口を作るものです。次のことを自動的に保証するものではありません。

- 要求や設計が正しいこと
- 実機が安全に動くこと
- 法令、規格、認証、契約に適合すること
- 正確な性能値や部品選定が決まること
- SysMLツールへそのまま読み込めること
- 人の設計承認や安全判断を置き換えること

安全、法律、認証、契約、セキュリティ、正確な性能値は、根拠を確認できる専門家と責任者が判断します。実施済みの検査と未実施の検査は、[07_VALIDATION_REPORT.md](07_VALIDATION_REPORT.md)に記録します。
