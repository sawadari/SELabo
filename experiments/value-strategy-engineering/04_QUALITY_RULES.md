# VSE候補データ 品質規則 v1.0.0

## 0. 判定
`pass` / `pass_with_provisional_assumption` / `fail` / `not_applicable` / `not_performed` を用いる。**schema pass ≠ 内容の真実 ≠ 戦略の有効性**。証拠が無い要素を増やしてGateを通してはいけない。

## 1. 基本規則
| ID | 規則 | 重大な失敗例 |
|---|---|---|
| Q-ORI-01 | 全主要要素は一意ID、origin、claim_state、decision_state、validity_state、confidence、source_refsを持つ | 推測を顧客確認済と表現 |
| Q-ORI-02 | 出典の原文・所在・日時・信頼性・公開権限を記録 | 根拠不明の売上値 |
| Q-ORI-03 | 顧客発言、観測、推論、仮想例、外部資料の主張は同一視しない | 仮想顧客の購買意向を実測扱い |
| Q-SCP-01 | 自社が制御できる手段と、外部顧客や競合の行動を区別 | 顧客購買を「設計済」と記述 |
| Q-SCP-02 | 目的、対象内外、時間軸、責任者候補を識別 | 市場全体を無条件に対象 |
| Q-ACT-01 | B2Bでは利用者、推進者、決裁者、予算責任者、購買、阻害者を必要に応じ区別 | 技術担当者の賛同で受注と断定 |
| Q-PRB-01 | 問題・症状・原因仮説を分離 | ツールを使わない理由を教育不足と断定 |
| Q-VAL-01 | 顧客価値、自社利益、利用者負担、外部影響の価値尺度を区別 | 自社利益＝顧客便益 |
| Q-HYP-01 | 重要仮説は予測、反証条件、検証方法を持つ | 「顧客は必要としている」と断定 |
| Q-HYP-02 | 競合する説明仮説と反対証拠を保持 | 都合のよい発言だけを抽出 |
| Q-HYP-03 | 機能価値、購買意向、支払意思、導入許容性を区別 | ニーズの有無から購買を推定 |
| Q-ALT-01 | 同じ問題に対する比較可能な代替案がある | 教育支援とWeb広告を同列比較 |
| Q-ALT-02 | 現状維持を原則含み、除外なら理由を記録 | 追加サービスしか選択肢にない |
| Q-ALT-03 | 戦略選択は資源配分、差別化、能力制約、非選択を扱う | 思いついた施策のリストを戦略と呼ぶ |
| Q-DEC-01 | 比較基準と決定権者を明示し、暫定選択を人の承認と混同しない | AIが戦略採用済みとする |
| Q-REL-01 | 全関係は存在するIDへ接続し、関係型・方向が妥当 | 参照先が存在しない |
| Q-REL-02 | 支持根拠と因果主張を分離し、因果の識別状況を明記 | 引用文に因果矢印を設定し立証済とする |
| Q-EXP-01 | 検証計画には対象仮説、観測指標、判断条件、交絡要因、実施状態がある | 反証不可能なアンケート |
| Q-EXP-02 | 経済効果・価格・市場規模には定義、母数、範囲、出典・比較条件を持つ | 根拠不明のROI 200% |
| Q-EXP-03 | 観察結果と介入の因果効果を混同しない | 商談化率が上がったから施策の効果と断定 |
| Q-SEC-01 | 個人情報、機密情報、外部送信、公開、契約は明示的な権限によってのみ扱う | 会話中の顧客名を公開GitHubへ送る |
| Q-OUT-01 | `10_vse_model.json`が唯一の候補意味ソースで、Markdown/CSVは投影 | 資料ごとに仮説が異なる |
| Q-JA-01 | 日本語の主語、比較相手、仮説/事実ラベル、単位を明確にする | 「高い効果」とだけ記述 |
| Q-GAT-01 | 40点Gateで初稿の過剰詳細化と重大欠落を検査 | 仮の数値を本格的な事業計画値に使う |

## 2. 要素の最低接続

以下は「必ず新規項目を生成しろ」ではなく、重要なつながりをレビューできるかという観点である。

- `Objective → Problem / Value → Hypothesis → Experiment`：なぜ検証するかをたどれる。
- `Problem → Alternative (status_quoを含む) → Decision`：同一問題に対する選択を説明できる。
- `Alternative → Capability / Intervention / Risk`：組織が実行できるかを確認できる。
- `SourceFragment → Evidence → Hypothesis`：どの主張が何に支えられるかを確認できる。
- `Intervention → Outcome` の矢印は**因果関係の証明ではない**。必要なら `causally_influences` の状態を別に記す。

## 3. 自動検査と人による検査

自動で比較的検査可能：JSON構文、Schema、ID重複、参照解決、関係語彙、状態の不正昇格、仮説の必須項目、未確認の数値表現のフラグ候補。

自動では十分に検査できない：顧客の真のニーズ、競合優位性、需要規模、因果効果、見積精度、法令適合、倫理的な適切さ、人が承認したかどうか。検証スクリプトはこれらを`not_performed`として残す。

## 4. 変更・差分

既存仮説に反証が入った場合、その仮説に `stale` または `superseded` を検討し、関連する選択、施策、実験計画を影響分析へ含める。消去せず変更履歴を保つ。AIは承認を付与しない。
